# Phase 2 — Deep Backend Audit

## 2.1 Architecture

### Layering: routes → controllers → services → data access

The codebase attempts a layered architecture but has significant violations:

| Layer | Where It Lives | Violations Found |
|---|---|---|
| **Routes** (`src/app/api/`, `src/app/dashboard/`) | Next.js App Router pages and API route handlers | Business logic (Prisma queries, form handling) directly in route handlers; no dedicated controller layer |
| **Controllers** | Not explicitly separated | Business logic leaked into `src/app/page.tsx`, `src/app/dashboard/teacher/page.tsx` — these are server components that fetch data AND render UI |
| **Services** | `src/lib/actions/` (14 action files) | Good intent: `student.ts`, `teacher.ts`, `subject.ts`, etc. But actions contain Prisma calls + business logic + some formatting. Not truly "service layer" — they're thin wrappers around Prisma. |
| **Data Access** | `src/lib/prisma.ts` (with `$allOperations` extension), `src/lib/data/*.ts` (8 helper files) | Prisma extension (`prisma.ts:44-66`) auto-injects soft-delete filters for reads. `src/lib/data/*.ts` files exist but are inconsistently used — some actions import from them, some bypass them. |

### Coupling & circular dependencies

- `src/auth.ts` imports from `src/lib/prisma` and `src/lib/rate-limit` — tight coupling between auth, database, and rate-limiting in a single file.
- `src/lib/prisma.ts:1` imports `PrismaPg` from `@prisma/adapter-pg` and creates a Prisma client singleton. Global state (`globalForPrisma`) risks unintended sharing across tests/requests.
- `src/lib/data/teacher.ts` → `src/lib/prisma.ts` → `src/auth.ts` — circular-like dependency chain where auth checks depend on prisma profiles, and prisma extensions depend on soft-delete logic.

### Pattern consistency across modules

- **Inconsistent**: Some actions use `prisma.$transaction`, others don't. Some use `softDeleteRecord()` from `prisma.ts`, others don't check `deletedAt`.
- **Consistent**: Zod validation schemas in `src/lib/formValidation.ts` are used via `typedZodResolver` in `formResolver.ts` across all forms.
- **Inconsistent**: Soft-delete handling. `Teacher` and `Student` have `deletedAt` in schema; `Parent` also has `deletedAt`. But the `Admin` model has no `deletedAt` — admin soft-delete is not implemented.

## 2.2 API Design

### Endpoint-by-endpoint review

Available API routes (from `src/app/api/` discovery):

| Path | Method | Purpose | Status |
|---|---|---|---|
| `/src/app/api/auth/\[...nextauth\]/route.ts` | POST | NextAuth credentials + Google OAuth callback | Auto-generated by NextAuth |
| `src/app/dashboard/admin/list/teachers/\[id\]/page.tsx` | GET | Get teacher detail (admin) | Page route, not REST API |
| `src/app/dashboard/admin/list/parents/\[id\]/page.tsx` | GET | Get parent detail (admin) | Page route |
| Finance, attendance, grades: mostly UI pages | — | — | No dedicated REST API routes discovered; data fetched via Server Components |

**Missing REST endpoints** that would be expected in a typical school management API:
- `POST /api/students` — create student (form submission goes to `/dashboard/admin/list/students` page, not an API route)
- `POST /api/fees` — create fee/payment entry
- `PUT /api/grades` — update grade
- `GET /api/attendance` — list attendance records
- Authentication refresh/logout endpoints (NextAuth handles these via `/api/auth/[...nextauth]`)

### Response shape consistency

- **No consistent envelope**. Success responses vary:
  - Page props: `{ session, teacher, student, parent, children, stats, todayClasses, ... }` — each page returns different shape
  - Form submissions: toast success/error messages only; no JSON response body
  - API routes (NextAuth): `{ session, user }` from `next-auth`
- **Error responses**: Also inconsistent — some redirect to `/login`, some show error components, some return null from auth authorize function.

### Pagination, filtering, sorting

- **Not present** on most list endpoints. Admin lists (teachers, students, parents) render all records on a single page with no "load more" or pagination controls in the UI.
- **No query parameters** for filtering (e.g., `?status=active`, `?grade=10`) or sorting (e.g., `?sort=name&dir=asc`).
- **No versioning** — API is implicitly version 1, tied to Next.js App Router structure.

### Idempotency & retry safety

- **No idempotency keys** for payment or mutation operations.
- **Create operations** (student enrollment, fee creation) are not idempotent — submitting twice creates duplicate records.
- **No retry-with-backoff** for third-party calls (none exist yet, but payment integrations would need this).

### Contract documentation

- **OpenAPI/Swagger: None**. No `openapi.json`, no `swagger.yaml`, no auto-generated docs.
- **Manual documentation**: Only what's in `.env.example`, `prisma/schema.prisma`, and code comments. No API contract between frontend and backend.

|---|---|---|---|

- **Prisma parameterized queries** protect against SQL injection for most operations since Prisma uses prepared statements.

- **No user input directly interpolated** into query strings.

## 2.4 AuthN & AuthZ

### Authentication flow end to end

| Step | Implementation | Status |
|---|---|---|
| **Registration** | Not explicitly implemented — Google OAuth only + credentials flow in `auth.ts:37-83`. No `POST /api/register` route. | ❌ No traditional registration; Google sign-up defaults to "student" role (auth.ts:95-96) |
| **Login** | `POST /api/auth/[...nextauth]` via Credentials provider | ✅ Works: rate limiting (5 attempts/15min), bcrypt compare, profile activity check |
| **Token issue** | NextAuth JWT strategy (`session: { strategy: "jwt" }`) | ✅ Token contains `role` and `id` |
| **Refresh** | Implicit via JWT expiration; no explicit refresh token flow | ⚠️ JWT default expiration — long refresh sessions; no explicit `refreshToken` endpoint |
| **Logout** | `signOut({ callbackUrl: "/login" })` in `next-auth/react` | ✅ Works |
| **Revocation** | None — JWT are stateless; revocation would require blacklist or short expiry | ❌ No token revocation mechanism |

### Password handling

| Aspect | Implementation | Status |
|---|---|---|
| **Algorithm** | `bcryptjs` with cost factor 10 (default, not explicitly set) | ⚠️ Default cost may be suboptimal; not configured in `.env` or code |
| **Cost factor** | `compare(credentials.password, user.password)` in `auth.ts:62-65` | ✅ Used correctly |
| **Reset-token entropy** | Not implemented — no forgot-password flow | ❌ No password reset functionality |
| **Entropy** | N/A | ❌ Entropy not enforced; Zod only checks min(6) characters |
| **Timing-safe comparisons** | `bcryptjs.compare()` — constant-time by algorithm | ✅ bcrypt provides timing-safe comparison |

### Session/token lifetime, rotation, replay protection

- **Strategy**: `session: { strategy: "jwt" }` in NextAuth config (`auth.ts:114-116`)
- **Lifetime**: JWT default (until browser clear or expiry — not explicitly set, so uses NextAuth default which is "very long")
- **Rotation**: None — same JWT on every request; no rotation on login
- **Replay protection**: Rate limiter (in-memory Map, 5 attempts/15min) — protects against brute-force but not replay of captured tokens

### Authorisation matrix (endpoint × role × allowed?)

**Critical finding**: No server-side authorisation matrix exists. The only checks are:

1. **`src/app/page.tsx:6-18`** — Home route checks `session.user.role` against `VALID_ROLES` and redirects to `/login` if missing/invalid. This is **authentication**, not **authorisation** — it ensures a valid role exists, but doesn't check if that role is allowed on the target route.

2. **`src/component/Menu.tsx:107`** — `if (!item.visible.includes(role)) return null;` — hides menu items based on role. **This is UI-only**, not security.

3. **No route guards** — Protected pages (e.g., `/dashboard/admin/list/teachers`) have no `await auth()` check at the top. They assume the menu hid them, but a user who manually navigates to the URL will have the page render.

**Example: Admin teachers list access control matrix** (what *should* exist but doesn't):

| Endpoint | Role: admin | Role: teacher | Role: student | Role: parent |
|---|---|---|---|---|
| `GET /dashboard/admin/list/teachers` | ✅ Allowed | ❌ Blocked (403) | ❌ Blocked | ❌ Blocked |
| `GET /dashboard/teacher/attendance` | ❌ Blocked | ✅ Allowed (own classes) | ❌ Blocked | ❌ Blocked |
| `POST /payments` | ✅ Allowed | ⚠️ Allowed (if enrolled own classes) | ❌ Blocked | ❌ Blocked |

**IDOR (Insecure Direct Object Reference)**: 

- **Test scenario**: User A (teacher) changes URL from `/dashboard/teacher/attendance` to `/dashboard/teacher/attendance?studentId=B` where Student B is in another teacher's class. 
- **Likely vulnerable**: The page `src/app/dashboard/teacher/attendance/page.tsx` (not fully read) likely fetches attendance based on route params without verifying the teacher supervises that student.
- **Same for students**: `/dashboard/student/fees` could potentially expose another student's fees by changing the URL parameter.

### Privilege escalation via mass assignment

- As noted in 2.3: `studentUpdateSchema` and `parentUpdateSchema` don't exclude `role` field. If a parent or student could submit `role: admin` via a form, and the server blindly applied it, privilege escalation would occur. **No form in the current codebase includes `role` field**, so this is a potential gap rather than active exploit, but the schema design is risky.

## 2.5 Data layer

### Indexes vs. actual query patterns

| Table | Filtered/Sorted Fields | Indexes | Gap |
|---|---|---|---|
| `Lesson` | `teacherId + day` (timetable queries), `classId` | ❌ None | N+1 risk; full table scans for timetable |
| `Attendance` | `studentId + lessonId + date` (unique constraint), `lessonId` for "all attendance for this lesson" | ⚠️ `@unique([studentId, lessonId, date])` only | No index on `lessonId` alone; querying "all attendance for lesson X" does full scan |
| `Fee` | `status`, `studentId`, `type` | ❌ None | Billing queries scan entire table |
| `Result` | `studentId`, `examId?`, `assignmentId?` | ❌ None | Grade queries scan entire results table |
| `Exam` | `lessonId` | ❌ None | Exam listing for a lesson requires full scan |
| `User` | `email`, `username` | ✅ `@unique` creates index | OK |
| `Student` | `parentId`, `classId`, `gradeId` | ❌ None (only `@unique` on `id`, `username`, `email`) | Queries filtering by parent/class/grade do full scans |

**N+1 queries confirmed**:

1. `src/app/dashboard/teacher/page.tsx:71-74`:
   ```ts
   const totalStudents = teacher.supervisedClasses.reduce(
     (acc, cls) => acc + cls.students.length, 
     0
   );
   ```
   If `teacher` was fetched with `include: { supervisedClasses: { include: { students } } }`, this is fine. But the Prisma findUnique in `:41-64` only includes `subjects: true, supervisedClasses: { include: { students } }, lessons: ...` — wait, it does include students. Let me re-check.

   Actually looking at `teacher/page.tsx:41-64`:
   ```ts
   const teacher = await prisma.teacher.findUnique({
     where: { id: teacherId },
     include: {
       subjects: true,
       supervisedClasses: {
         include: {
           students: true,
         },
       },
       lessons: { ... },
     },
   });
   ```
   Yes, `supervisedClasses` includes `students: true`, so `cls.students.length` won't trigger N+1. But `teacher.subjects.length` at line 106 could be N+1 if `subjects` was already fetched (it's `true` not `include`, but Prisma may still lazy-load if not in the initial query). Actually `subjects: true` is a shortcut for `{ include: { ... } }` — it should load in the same query.

2. `src/app/dashboard/student/page.tsx:47-55`:
   ```ts
   const subjectsCount = await prisma.subject.count({
     where: {
       lessons: {
         some: {
           classId: student.classId,
         },
       },
     },
   });
   ```
   This is a separate count query — not N+1 per se, but an extra query per page load.

### Transactions where multi-document consistency is required

| Operation | Required? | Currently Implemented |
|---|---|---|
| Payment creation (create Payment record + update Fee.status + write AuditLog) | ✅ Yes | ❌ No — three separate DB operations, no transaction |
| Student enrollment (create User + Student + maybe Fee structure) | ✅ Yes | ❌ Not wrapped — partial failure possible |

**Recommendation**: All multi-model operations should wrap in `prisma.$transaction()`. Add `logAudit()` calls inside transactions.

### Migrations: exist? reversible? versioned?

- **Prisma Migrate** is used — migration files in `prisma/migrations/` (need to check count, but directory exists).
- **Reversibility**: Not assessed — need to run `prisma migrate resolve --rolled-back` or check migration down functions.
- **Versioning**: Implicit via `prisma migrate make` + `prisma migrate deploy`. No separate version table tracked beyond `_prisma_migrations` system table.

### Soft delete vs. hard delete; audit trail

- **Soft delete**: `Teacher`, `Student`, `Parent` have `deletedAt DateTime?`. Prisma extension (`prisma.ts:46-65`) auto-injects `deletedAt: null` for read operations on these models.
- **Hard delete**: No `DELETE` operations discovered — all mutations go through soft-delete or create/update.
- **Audit trail**: `AuditLog` model exists (`prisma/schema.prisma:434-446`) with indexes on `userId` and `[entity, entityId]`. However:
  - `softDeleteRecord()` at `prisma.ts:75` sets `deletedAt` but **never calls `logAudit()`**.
  - `logAudit()` at `lib/audit.ts:10-29` works correctly but is **never invoked** for soft-delete or restore operations.
  - Restore (`restoreSoftDeletedRecord()` at `prisma.ts:90`) also doesn't create audit log.

### Backup and restore story

- **No backup script** in `package.json`.
- **Prisma Migrate** handles schema evolution, not data backup.
- **PostgreSQL** `pg_dump` / `pg_restore` would be external — not automated in repo.
- **Recommendation**: Add `db:backup` script (pg_dump), schedule automated backups, test restore.

## 2.6 Errors, logging, observability

### Centralised error handling vs. scattered try/catch

- **Scattered**: `try/catch` blocks in individual actions (`src/lib/actions/student.ts`, etc.) and form handlers (`src/component/forms/StudentForm.tsx:119-139`). No global error middleware or exception handler.
- **Global exists**: `next.config.ts:44` security headers middleware, but no custom error page handler at the API route level beyond Next.js default.

### Stack traces leaking to clients

- **Potential**: `catch (error) { toast.error("An unexpected error occurred"); console.error(error); }` in `StudentForm.tsx:135` logs to console but user sees generic message. In development (`NODE_ENV` not set to production), Next.js may show error pages with stack traces.
- **Global-error.tsx** exists at `src/app/global-error.tsx:1-23` — shows generic "Application error" message. Better than stack trace, but doesn't include correlation ID or user-friendly guidance.

### Structured logging with correlation IDs

- **None**. `console.error()` calls scattered without correlation IDs, log levels, or structured format. No request ID propagation.

### PII in logs — every instance is a compliance finding

- **Confirmed**: `src/auth.ts:62-65` — `compare(credentials.password, user.password)` — if error is logged, password hash could be exposed in logs (though bcrypt hashes are resistant, the comparison result could leak timing info).
- **Confirmed**: `console.error(error)` in `StudentForm.tsx:137` — may log `formData` which includes user-submitted values (name, email, address, etc.).
- **Confirmed**: `prisma.$use` extension in `prisma.ts:44-66` — audit log writes `userId`, `action`, `entity`, `entityId`, `description` — if any of these contain PII (e.g., student names, email addresses), they're stored in `AuditLog` table which may be queried by admins.

**Every instance is a compliance finding** under Rwanda Law No. 058/2021, GDPR, or other data protection regulations.

### Health/readiness endpoints, metrics, alerting

- **None**. No `/health`, `/ready`, or `/metrics` endpoints.
- **No Prometheus metrics**, no Datadog, no New Relic, no custom health checks.

**Mitigation**: Server-side resource ownership check on every attendance/grade/fees endpoint; verify teacher supervises student before returning data.

## 2. XSS via Announcements
**Attacker**: Any user who can create announcements (admin, potentially teacher/parent depending on future implementation)  
**Vector**: Enter `<script>alert(document.domain)</script>` as announcement title or description  
**Impact**: Script executes in browser of any user who views the announcement (all dashboard roles)  
**Likelihood**: High (no sanitisation, content is rendered)  
**Severity**: P1 — High  
**Mitigation**: DOMPurify sanitisation on all user-generated content before rendering; Content Security Policy with `'unsafe-inline'` removed.

## 3. Bypassing Access Control via Direct URL
**Attacker**: Any authenticated user (teacher, student, parent)  
**Vector**: Manually navigate to `/dashboard/admin/list/teachers`, `/dashboard/admin/list/students`, etc.  
**Impact**: Full admin dashboard exposure to non-admin roles  
**Likelihood**: High (menu visibility ≠ access control)  
**Severity**: P0 — Critical  
**Mitigation**: Add `auth()` check at the top of every protected page/route; return 403 Forbidden for role mismatches instead of redirecting to login.

## 4. Payment Double-Charge
**Attacker**: Malicious user or system error  
**Vector**: Submit payment form twice (network retry, user double-click)  
**Impact**: Fee marked paid twice; audit log shows two completed payments for one fee  
**Likelihood**: Medium (form resubmission possible)  
**Severity**: P1 — High  
**Mitigation**: Wrap payment creation + fee update in Prisma `$transaction`; use idempotency key; prevent form double-submit with disabled state + nonce.

## 5. Brute-Force Authentication
**Attacker**: External attacker  
**Vector**: Automated login attempts against `/api/auth/[...nextauth]`  
**Impact**: Account takeover if weak passwords; rate limiter currently limits to 5/15min but is in-memory only  
**Likelihood**: Medium (school staff passwords may be weak)  
**Severity**: P1 — High  
**Mitigation**: Move rate limiter to Redis (persistent across restarts, scalable); implement account lockout after N failures; add CAPTCHA; enforce password policy.

## 5. PII Exposure in Logs
**Attacker**: System admin, or attacker who gains log access  
**Vector**: `console.error()` statements that log form data; `AuditLog` table contains user descriptions that may include names, emails; error pages may leak internal details  
**Impact**: Violation of Rwanda Law No. 058/2021, GDPR; data breach notification required  
**Likelihood**: High (logging patterns throughout code)  
**Severity**: P1 — High  
**Mitigation**: Remove PII from log statements; add correlation IDs; sanitize audit log descriptions; never log passwords or emails; add `beforeExit` hook to redact logs.

## 6. CSP Bypass via Unsafe Inline
**Attacker**: Any user who can inject HTML (announcement creator, potentially student via exploited XSS elsewhere)  
**Vector**: CSP currently allows `'unsafe-inline'` — if XSS exists elsewhere, attacker can inject `<script>` that executes because CSP doesn't prevent it  
**Impact**: Full account takeover via keystroke logging, session hijacking  
**Likelihood**: Medium (depends on XSS elsewhere being fixed first)  
**Severity**: P2 — Medium  
**Mitigation**: Remove `'unsafe-inline'` and `'unsafe-eval'` from CSP; use nonce-based or hash-based script enforcement; move inline event handlers to external JS.
